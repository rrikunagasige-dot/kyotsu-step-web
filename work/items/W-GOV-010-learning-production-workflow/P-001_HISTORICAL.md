## 4. AIに渡す仕事と提出物を変更する

同じAIで段階を分けて実行できる。別AIを使う場合も同じ提出形式を使う。役名を分けただけで独立監査になったとは言わず、根拠と検算経路を分ける。

### A. 原資料と既習状態の確定

提出物：SOURCE_MAP、用語・記号台帳、前提知識一覧。

原問・条件・図・最終的に要求される答えの型に加え、番号の付いていない定義・性質・証明の接続・説明文も取り出す。質問の全件対応だけで、教科書内容全体の対応を済ませない。既存アプリの答えをそのまま正解根拠にせず、WordのOMML・本文・既存の原典監査と照合する。未読・不鮮明な箇所は未確認と書く。

### B. 穴のない完全解法

提出物：問題ごとの完全解法。

何を求めるか、使える条件、必要な方針、各操作、適用条件、途中結果、最後の結論まで先に書く。小学校・中学校・高校で解答過程を説明するように、操作の対象と順序を見せる。「整理すると」だけで複数操作を飛ばさない。

解法を、画面の既存順序へ無理に合わせない。第一タイトルの「次数別に集める」手順を循環小数や根号へ機械移植しない。

### C. 教える順序と能動的な穴

提出物：TEACHING_PLAN。各ノードに次を記載する。

| 項目 | 必須内容 |
|---|---|
| 解決したい小目標 | 生徒が今、何を求めるか |
| 今見える前提 | 条件、既習事項、前段階のどの結果を使えるか |
| 操作を選ぶ理由 | なぜこの計算・比較・置換をするか |
| 一段の操作 | 対象となる式、行う操作、得られる式 |
| 根拠・条件 | 定義、法則、符号、分母が0でないこと等 |
| 生徒の行為 | 方針選択／式生成／条件判断／導出／計算／意味の解釈など |
| 穴の位置と理由 | なぜここを本人に担わせるか。置かないならその理由 |
| 残す結果と次の用途 | どこで再利用するか、問題全体の何を完成させるか |
| 表示と解放 | 本文・式・選択肢・図・前提欄を、回答前後のどちらで見せるか |

未知の名称・新しい事実は先に教える。そこを推測させる穴にしない。計算結果の穴と推導・理由の穴を区別し、どちらかを数だけで増やさない。

### D. 本文と図の制作

提出物：読める教材全文、図・表の設計、選択肢と誤答理由。

本文は「今の結果が次に何を可能にするか」をつなぐ。問句を並べるだけにせず、着眼・操作・根拠を示す誘導文を書く。会話は必要な箇所だけに置く。定義・性質・必要な証明・例題の関係を明確にし、未知語を当てる形にしない。

原問→完全解法→教える順序→穴→本文→画面、の順に設計する。出来上がった文章の適当な数字を後から穴にする方式を標準にはしない。

### E. 反証・初学者監査

提出物：FINDINGS。各指摘はノードID・該当文／式・問題点・修正方針を持つ。

1. この場面の生徒が、前に見えた情報だけで一段進めるか。
2. 途中式が正しいだけで、必要性や根拠が抜けていないか。
3. 一つの選択肢で複数の未学習判断を代行していないか。
4. 結論→前段のやり直し、別問題への往復になっていないか。
5. 答える前の本文・ヒント・図・履歴・前提欄に、その穴の具体解答が出ていないか。
6. 既習公式の参照まで「漏洩」と誤判定していないか。既知結果を使う学習と、その結果を初めて作る学習を区別したか。
7. 支援を減らした箇所でも、その方法は本当に先に学習済みか。
8. スマホだけで考えられ、紙での長い暗算・筆算を暗黙に要求しないか。

重大項目がFAILまたはUNVERIFIEDなら、文章の見栄えや総合点で通さない。AIの監査合格は、ユーザーの教育的受入を代行しない。

## 5. 承認例と失敗例を、再利用できる評価資料にする

| 由来 | 保持する評価例 | 別の単元へ移す原則 |
|---|---|---|
| N01の正式受入版 | 対象→理由→局所計算→結果保持→全体へ戻す | 必要な小目標と結果の用途を追えること |
| W028の拒否例 | 補助式を増やしても、前後の説明がつながらない | 「詳しい」の判定を行数・穴数に置き換えない |
| W029の全体順序修正 | AとBの計算を往復せず、各部分を完成して使う | 例題単位の独立性と再利用関係を区別する |
| W030の穴改善 | 結果だけでなく、係数を集める式や変形を本人が作る | 方法・式生成・理由の能動性を検査する |
| W031の受入版 | 短い等式、等号位置、項・因子の継続、番号と余白 | 文章を削らず、数学の行構造と表示幅を分ける |
| 集合の既存版 | 今の問いに必要な前結果だけを参照する | 折りたたみ後にも必要な条件・結果を見失わない |

評価資料は、元の失敗／修正／受入のソースと指摘を持たせる。候補が自分で作った答案を自分の合格見本に登録しない。多項式に似た文面を出せることを一般化の証拠にしない。

第二タイトルでは、循環周期・符号と0・平方根の非負性・有理化・二重根号を別々の評価例にする。現時点でモデルの重みを追加学習したとは主張しない。まず、実行時の制作規約と評価データを版管理し、同じ失敗を検出できるか測る。

## 6. コードは、教材の意味と表示を別々に受け持つ

制作側の設計データを共通化し、既存TextbookUnit／readingFlowへ変換する。意味・解く順序・穴の理由をrendererに推測させない。

```json
{
  "unitId": "math-numbers-expressions-n07",
  "baselineSource": "22bc43ba53fa87bb85e82e18a25db13a5c8a485c",
  "problemId": "N07-Q09",
  "nodes": [{
    "id": "n07-q09-scale",
    "sourceRefs": ["Word:N07-Q09"],
    "knownRefs": ["n07-q09-period"],
    "goal": "循環部分をそろえて引ける式を作る",
    "operation": "倍率の選択",
    "reason": "元の数と同じ小数部分を作るため",
    "conditions": ["周期は2桁", "最小の10の累乗を選ぶ"],
    "learnerAction": "方針選択",
    "interaction": {"kind": "choice", "answer": "100", "choices": ["10", "100", "1000"], "blankReason": "周期と同じ桁数だけ小数点を動かす倍率を選ぶ"},

    "view": {"role": "導出", "equationGroup": "n07-q09-scaled-equation"}

```

これは具体的な一ノードを使った契約の抜粋であり、N07全体の確定設計ではない。上の仮IDや文面をそのまま教材へ生成しない。実装時にはschemaで型・参照・条件・表示時点を確定する。

設計データから、本文、段階、前提参照、保存する結果、空欄、選択肢、数式番号、source対応表と検査対象一覧を生成する。表や図も同じ正本データを参照し、rendererへ別の数学の値を埋め込まない。

教える順序は、設計者が明示したorderedNodeIdsと段階境界を正本にする。依存グラフはその順序の妥当性を検査するもので、任意のトポロジカル順や画面の長さから教える順を自動決定しない。画面幅が変えられるのは式の物理的な改行であり、学習ノードの順序ではない。

### 6.3 長い教材を扱う、画面テンプレート

一つのNを一度に全部開く方式には戻さない。意味のある小目標が完了し、次に使える結果ができる所を段階の境界にする。文字数や画面の高さだけで本文を切らない。

| 領域 | 表示する内容 | データ上の条件 |
|---|---|---|
| 現在の段階 | 短い目標、問題／定義／証明／例題の役割 | 同じ大見出しを何重にも重ねない |
| 使う条件・前の結果 | 今の未回答問題に必要な正本ブロックだけ | activeItemIdからknownRefsを取得。過去の正答が必要な結果は確定後に表示 |
| 本文と式のつながり | 着眼・理由→式／判断穴→回答後の根拠→次の一段 | 異なる式を見た目だけで等号の連鎖にしない。本文を削って短くしない |
| 段階の結論 | 本人が確定した結果と、次に何へ使うか | source IDで参照し、結論の数学を別コピーとして管理しない |
| 過去の学習 | 結論を残した要約、必要時の全文展開 | 履歴を閉じても結果が見える。未確定の答えは保存済み結論にしない |

短い等式は一行、変形は等号揃え、普通の継続は演算子・項・因子の意味を保つ。番号は式の幅から独立させ、重なるときだけ番号を下へ送る。間隔の所有者を一つにし、段落・式・外枠の余白を足し重ねない。空欄は集合と同じ操作部品、選択肢は一候補一カードを継承する。

誤答では先へ進めず、正答後の説明と結論を読んで次の段階へ進める。制作側のnode分類や内部IDを、説明の代わりとして生徒の画面へ出さない。

## 7. 数学・文章・表示の検証を混同しない

| 検証の種類 | 自動化できるもの | AI／人が読む必要があるもの |

| 出典・構造 | 全原問の対応、参照先、重複ID、未来の結果参照、未定義キー | 用語導入の自然さ、元問題の要求が教材へ残るか |
| 数学 | 正確な分数計算、平方、条件付き変形、境界値、反例、誤答検査 | 完全解法の論理、なぜその操作をするか、条件の説明 |
| 穴 | 選択肢の型、正解重複、表示解放、直接的な具体答えの露出 | 意味ある判断か、単なる転記・未知語当てにならないか |
| 文章 | 用語・記号の参照、内容欠損、定型句の候補検出 | 既知→新情報、接続、段落・例題全体の流れ |
| 数式表示 | source token保存、MathML構造、実境界、等号・番号・余白 | 式変形と継続の区別が見て分かるか |
| 実動作 | 誤答→ヒント→再回答、前結果、履歴、reload、reset、進捗移行 | スマホだけで学習を続けられるか |

数値サンプル検算は反例探索に使えるが、一般式や全実数についての証明にはしない。第二では多項式用の検算だけを流用せず、正確な有理数、絶対値の符号分岐、主平方根、非零分母、因子選択の条件を扱う。

特に、N10の原証明の条件はa>0,b>0として保持する。一般に拡張できるという別の知識を、原問題の条件の黙った変更には使わない。

分数・根号はparse成功を合格基準にしない。分母が2のはずの式が集合の括弧になる既往不具合を含め、N07-Q08・N10-Q16・NE02-Q10/Q12の既存修正・全選択肢を守る。根号の作用範囲、分子・分母、平方の作用範囲を意味構造でも検査する。

## 8. 確認方式は、完成した公開アプリへ一本化する

| 項目 | 旧方式 | 新方式 |

公開先は、陸君が示した既存アプリを使用する。

https://rrikunagasige-dot.github.io/kyotsu-step-web/?v=22bc43ba#/learning/textbook/math-numbers-expressions-n01

なお、vは読み込みを更新するための値で、古い版を恒久選択できる仕組みではない。公開履歴には実際のソースSHA・build・検査結果を保存し、必要な復元はその版を再公開する手順で行う。

### 実行する順序

対象確定・原資料確認 → 完全解法と教材設計 → 承認された範囲の実装 → 制作側の数理・文章・漏洩・UI検査 → compile → 既存Pagesへ公開 → 公開版のSHAと対象Nを検証 → アプリURLを提示 → ユーザーの受入／修正を記録。

原則の公開単位は一N。一つの概念・問題ごとの事前点検は制作側で行い、ユーザーへの確認票を穴ごとに増やさない。代表Nの試運転を先に行う。複数Nの一括実行を後で明示承認した場合は、同じ範囲の実装承認をNごとに取り直さない。

ユーザーの要修正があれば、該当箇所・根本原因・同型箇所を調べて直す。承認済み目的の範囲内の誤り修正は毎回新たな大提案へ戻さない。問題の条件や学習目標を変更する必要がある場合は、変更案を先に示す。

公開前検査に失敗した版は公開しない。公開後に重大不具合を確認した場合は、証拠を保存して対象を修正し、必要なら直前の検証済み版へ戻す。失敗版を完成扱いにしない。

### N07-Q09から見える、工程改善の具体例

現在は「100倍・100xの式・99x=69」を一つの選択で答える。新工程では、まず次の思考を別々に設計する。

| 段階 | 生徒が行うこと | 残すもの／次の用途 |
|---|---|---|
| 周期を見る | 69が二桁の繰り返しであると読む | 小数点を何桁動かすかを考える |
| 方針を決める | 同じ小数部分をそろえる最小倍率を選ぶ | 掛ける数を決める |
| 式を作る | 100倍した等式を構成する | 元のxの式と対応させて引く |
| 操作を選ぶ | 引けば循環部分が消えることを判断する | 比較する二式と引く順を決める |
| 左辺を作る | 100x−xを係数の式でまとめる | 99xという左辺を得る |
| 等式を解く | 99で両辺を割る | 分数69/99を得る |
| 整える | 分子・分母の共通因数で約分する | 最終的な23/33と、有理数である理由をつなぐ |

説明文の時点も設計する。倍率を答えた後なら「100倍した式は、元の式と小数部分が同じです。この二つを比べます」と結果をつなげる。引く操作を選んだ後なら「同じ循環部分を引くと、その部分は0になります」と根拠を確認する。倍率や引く操作を問う直前に、その具体答えを本文で言わない。

これは方法を示す設計例であり、穴の最終個数や既存IDの置換を確定するものではない。既存Q09/Q10の役割との重複、直前の一桁周期の学習をどこまで省けるか、旧進捗をどう保持するかはN07全体設計で決める。

「100倍でも循環部分がそろう」という正しい式を、別問題で一律に数学的誤答とはしない。「最小」という問いの条件に合うかと、等式そのものが正しいかを分けて検査する。

## 12. 効率の上げ方も、具体的に決める

1. 原本・規則はハッシュと適用範囲を記録する。各問題前には該当規則と過去の同型失敗だけを読み、毎回全チャットを再投入しない。
2. 全体の解法計画を作ってから生成する。補助文を継ぎ足す再帰的修理を新規の標準経路にしない。
3. 決定的生成で、同じ設計から同じアプリデータを作る。本文、参照、番号、検査リストの手作業での二重管理を減らす。
4. 対象Nの変更なら、そのNの全件検証と関連回帰を行う。共有renderer・進捗・数式変換の変更なら影響する既承認単元へ広げる。毎小修正で全科目を同じ深さで再実行しない。
5. 数学の検算と独立した静的検査はまとめて実行できる。書き込み・進捗移行・公開の依存は順番を守る。
6. 検証済み結果の再利用は、教材内容・renderer・schema・ブラウザ／フォント条件が一致する場合だけ。新しいHEADへ古いPASSを付け替えない。
7. 同じ候補を一度buildし、その成果物を検査して公開する。公開後はSHAと成果物の一致、対象Nの実操作を照合する。
8. CI待機中は同じWorkの原典照合・文章監査・記録など、承認済みの独立作業を進める。未確認コードの重ね書きや、承認されていない別教材の量産をしない。

改善効果は、初回提出後のユーザー修正件数、同型不具合の再発、影響範囲外の差分、生成・検査・公開の時間と再実行回数で測る。穴の数、文章の長さ、AIの自己採点は品質指標の代わりにしない。現時点で速度が何倍になるとは約束しない。
